# Only callers admitted by the resolved account configuration may create Part lot information

Dedicated Web add-lot and supported MCP nesting under an existing Part require that enclosing Part’s edit authority. A concrete standalone REST create delegates the original create attribute to the associated Part; class or unassociated fallback uses parts.edit. Creation dependent on a new enclosing Part follows that creation guard. Movement first checks source move and owner authority; a new destination invokes create on the concrete new lot, delegating create to its associated Part, rather than the existing-target move/owner check. An accepted Project build requires Project read and global parts_stock.withdraw; its configured new-output-lot creation does not add output-add or per-lot owner authority.

## Rationale

Authority is supplied by the resolved User’s stored Permission overrides and the consulted Group chain. Explicit User values win; unresolved inheritance is denied. An authenticated token already carrying a disabled User is refused before permission lookup. Anonymous Web requests resolve the reserved anonymous User identity. PAT and OAuth role/scope ceilings are applied before inherited permission resolution and cannot enlarge User authority. REST and KiCad require authenticated api.access_api; MCP requires authenticated api.use_mcp and endpoint enablement, with editing enablement on the explicit write processors. The initiating API client, AI agent or KiCad client remains the caller; its authenticated User supplies authority rather than a fictitious stored caller registry.
